# DigiLegacy 路线图：从「持有者的规划台」到「家人能执行的工具包」

> 状态：提案（未实施）。所有引用均指向 `main` 分支 `d54aa54` 的实际代码行号。
> 判断基准只有一条：**家人拿到东西后，能不能在没有任何人帮助的情况下走完全程。**
> 测试数量、功能数量、代码行数都不参与这条判断。

---

## 一、定位复核

产品自称的六段链路：

> 资产发现 → 分类登记 → 处置规划 → 法律文书 → 到期触发 → 家人执行

首屏承诺是 **「给家人留下工具包，而不是一堆谜题」**（`README.zh-CN.md:7`）。

这条承诺的主语是**家人**，不是持有者。但当前产品的重心几乎全在持有者一侧：9 个功能视图（`src/views/`，另有 NotFound）、50 个 IPC 命令、152 条平台库、三级确认链——都是持有者在自己电脑上操作的东西。家人一侧的产物只有三样：一份 HTML、一个原始 JSON、一个统计 JSON。

**结论：项目真正的短板不在「持有者能不能规划」，而在「规划完之后，家人能不能接得住」。** AI 如果要加，必须加在后半段，加在前半段只会让已经很重的部分更重。

## 二、当前成熟度（按六段逐项判定）

| 阶段 | 对外承诺 | 代码现状 | 判定 |
|---|---|---|---|
| 资产发现 | 问卷帮你想起忘记的账号 | 问卷勾选只用于显示计数（`DiscoverView.vue:20,233`），不影响平台筛选 | **弱**：装饰性 |
| 分类登记 | 152 平台 / 16 分类 | 数据完整，但 152 条里只有 5 条带 `data_source`（`platform_data.rs:72`），147 条无出处、无复审日期 | **强但不透明** |
| 处置规划 | 六种处置方式 | UI 完整；选「继承」不强制填继承人（`AssetDetailView.vue:73` 仅条件渲染，无校验） | **强但无约束** |
| 法律文书 | 可打印报告 + ZIP 工具包 | 预览含平台政策段（`ReportView.vue:93`），**后端导出没有这段**（`report.rs` 无相关字段）；报告恒为中文（`report.rs:159`） | **中：预览与导出不一致** |
| 到期触发 | 三级确认链 | 本机可跑；SMTP 只能靠环境变量（`notify.rs:6-8`，界面自己也这么写：`i18n/index.ts:446`），无测试发送 | **中：普通人配不起来** |
| 家人执行 | 按平台逐一办理 | 向导只存在于**持有者的本机应用里**；家人拿到的工具包是 HTML + 原始 JSON；恢复码、备份位置、凭据获取方式均无指引 | **弱：链路在此断开** |

### 已确认的七处「承诺与实现不一致」

1. **导出比预览少内容**。预览第 4 节渲染 `platformPolicy`（`ReportView.vue:93`），后端 `render_report_html` 的四、处置安排只输出处置方式与继承人姓名（`report.rs:196-206`），不含平台政策、所需材料、办理难度、预计时长、官方链接。持有者看到的是完整指导，家人拿到的是删节版。
2. **导出比预览少字段**。预览显示继承人联系方式（`ReportView.vue:91` 的 `heirInfo` 传了 `contact`），`asset_row` 只输出 `heir_name`（`report.rs:116`）。
3. **报告永远中文**。`report.rs:159` 硬编码 `<html lang="zh-CN">` 与中文标题，英文用户导出的仍是中文文档；而预览走 i18n 是英文。
4. **ZIP 权限与报告/备份不一致**。报告与备份走 `fsutil::write_private`（`commands.rs:356,621`），ZIP 走裸 `std::fs::write`（`commands.rs:395`）——而 ZIP 里的 `02-资产清单.json` 含全部账号标识。
5. **问卷不驱动任何东西**。`checkedItems` 只参与 `checkedCount` 显示，`goToStep(2)` 直接执行（`DiscoverView.vue:329`），与问卷答案无关。
6. **`is_confirmed` 恒为 true**。插入硬编码 `is_confirmed=1`（`db.rs:450`），更新也置 1（`db.rs:494`）。`DashboardStats.unconfirmed_count` 永远为 0，界面不展示，是一个死指标。
7. **「AI 接口已预留」不成立**。官网中英双站都写「AI 辅助政策问答（接口已预留）」（`docs/index.html:357`、`docs/zh/index.html:352`），但全代码库搜索 `AI|LLM|GPT` 零命中，没有任何接口。

### 已确认的四处结构性缺口

8. **完成度指标口径过窄**。`completion_percentage` 只统计 `disposal_method != 'no_action'`（`db.rs:1772-1793`）。选「继承」但没填继承人、没存凭据、没开触发链，照样算 100%。这是最容易误导人的那种指标。
9. **继承人只有一个人**。`user_profile` 是单组 `heir_primary_*` 字段（`models.rs:171-174`），资产层的 `heir_name` 是自由文本。没有多继承人、没有分配比例、没有独立的执行人角色——但文案里反复出现「遗产执行人」（`i18n/index.ts:484`），实际发信对象是 `heir_primary_email`（`notify.rs:561-565`）。
10. **政策库无溯源、无复审**。只有 5 条用 `with_source` 构造，其余 147 条 `PlatformEntry::new` 的 `data_source` 为空；`official_policy_url` 多为平台首页（`https://www.zhihu.com`、`https://weixin.qq.com`）而非政策页；`inheritance_form_url` 152 条全空。
11. **备份导入是整库替换**。`import_backup_json_db` 先 `DELETE FROM digital_assets / user_profile / check_in_log`（`db.rs:1361-1365`）再写入，导入前不自动快照，也没有「合并」选项。

## 三、AI 应该放在哪一层

### 硬约束（门禁，不是加权项）

| 门禁 | 出处 | 判定方式 |
|---|---|---|
| G1 默认零联网 | `AGENTS.md:38`、`README.zh-CN.md:38`、`tauri.conf.json:24` 的 CSP 只放行 `'self'` 与 `ipc:` | 默认配置下不产生任何网络请求 |
| G2 家人侧可离线使用 | 家人不一定有网、装不了软件、看不懂英文 | 工具包在断网电脑上双击可用 |
| G3 安装包增量 ≤ 50MB | 现在 3.5MB，体积本身就是卖点（`README.zh-CN.md:95`） | `tauri:build` 产物对比 |
| G4 CI 不依赖外网 | `scripts/verify.sh` 与 GitHub Actions 必须确定性通过 | 测试中无真实 API 调用 |
| G5 不需长期运维模型 | 单人维护的项目 | 无自建推理服务 |
| G6 解决真实痛点 | 见第二节：断点在家人侧 | 能通过「30 分钟家人演练」验收 |

### 五个候选方案

| 方案 | 核心思路 | 优点 | 缺点 | 成本 | 适用场景 |
|---|---|---|---|---|---|
| **A 运行时 BYOK 问答** | 应用内填 OpenAI 兼容端点与 Key，持有者提问 | 能力上限最高；零运维 | 家人侧无网即失效；Key 管理、提示词注入、数据出境都要自己兜；CSP 需放宽 | 中（后端 HTTP 通道 + 沙箱 + 脱敏） | 专业用户，且只服务持有者 |
| **B 作者期 AI（生成后冻结）** | 持有者在规划阶段用 AI 生成「家人 FAQ / 人话版政策 / 执行顺序」，输出为静态内容打包进工具包 | 家人零 AI、零网络；完全不动运行时契约；可人工审校后冻结 | 内容会过时；生成质量依赖持有者审校 | 低-中（一次性生成 + 审校 UI + 打包） | **本项目的正解**：AI 只在作者期出现 |
| **C 内置本地小模型** | 打包 1.7B–4B GGUF | 离线推理；无需 Key | 安装包涨到 1–2.5GB（违反 G3）；分发与 CI 成本高 | 高 | 硬件基线稳定的产品 |
| **D 官方托管服务** | 自建账号 + 云端模型 | 体验最顺 | 直接违反 G1；数据出境；运维成本 | 最高 | 与定位不相容 |
| **E 无 LLM 的规则/决策树** | 结构化问答树 + 模板拼装 + 政策字段渲染 | 零依赖、零网络、可测性最好、确定性 | 不能处理自由表达 | 低 | 覆盖 80% 的确定性问题 |

### 打分

| 门禁 | A | B | C | D | E |
|---|---|---|---|---|---|
| G1 默认零联网 | 过（默认关） | 过 | 过 | **不过** | 过 |
| G2 家人侧离线 | **不过** | 过 | 过 | **不过** | 过 |
| G3 体积 ≤50MB | 过 | 过 | **不过** | 过 | 过 |
| G4 CI 无外网 | 勉强（需 mock） | 过 | 勉强（需模型桩） | **不过** | 过 |
| G5 无需运维模型 | 过 | 过 | **不过** | **不过** | 过 |
| G6 解决家人侧痛点 | 弱 | **强** | 中 | 中 | 中高 |

### 选定：E 作底座 + B 作增值

- **E 先做**：把「家人会问的问题」做成确定性决策树，覆盖 80% 场景（先找谁、要什么材料、钱在哪、多久、能不能不公证）。这些答案本来就在平台库里，只是没被组织成面向家人的形式。
- **B 后做**：AI 在**作者期**运行一次，产出「个性化 FAQ + 人话版政策 + 优先级排序」，持有者逐条审校后冻结为静态文件进 ZIP。家人侧看到的仍是纯静态 HTML，零网络、零模型、零 Key。
- **A 不作为产品能力**，但 B 的生成通道可以复用 A 的技术底座（Rust 层 HTTP、用户自配端点、默认关闭）。这样 A 的工程投入不浪费，但不会以「AI 助手」的形态出现在家人面前。
- **C / D 明确不做**。

**这是对上一轮建议的修正**：上一轮选了「BYOK 运行时助手 + 本地模型包」，那是从「持有者想用 AI」出发的。按定位重新推演后，正确落点是「AI 只在作者期出现，产物冻结给家人」。运行时 AI 服务的是已经知道答案的人，作者期 AI 服务的才是真正需要帮助的人。

## 五、AI 边界（写进代码，不靠自觉）

**三条红线**

1. 不做官方托管 AI 服务、不做账号体系、不做云端推理。
2. AI 不写库、不生成法律意见、不杜撰平台政策或链接。没有来源就写「未核实」。
3. 凭据（`credential_enc`）、账号标识（`account_identifier`）、继承人联系方式（`heir_contact`）永不进入任何 AI 请求。白名单在 Rust 侧实现，不依赖提示词。

**两个必须**

1. 传输必须在 Rust 层（复用 `heartbeat.rs` 的 curl 子进程模式与 `vault::validate_external_url:141` 的协议白名单），**不改 `tauri.conf.json:24` 的 CSP**。一旦前端直接 `fetch`，就必须放开 `connect-src`，安全面立刻扩大。
2. AI 输出只有一种合法去向：**持有者审校后冻结进工具包**。不做运行时问答、不做后台自动生成。

**明确不做**

- 法律意见生成（责任无法承担）
- 资产自动分类（确定性规则更准更便宜）
- 聊天式交互界面（家人不需要聊天，需要清单）
- 任何形式的遥测或使用统计上报

## 七、不做什么

- 不做手机端（维护成本翻倍，先证明桌面版有人用）
- 不做云同步（与 no-server 冲突）
- 不做社区政策库（没有审核能力时，错误信息比没有信息更危险）
- 不做账号交易/代办理（法律与合规风险）
- 不在 P0–P3 完成前做 AI
